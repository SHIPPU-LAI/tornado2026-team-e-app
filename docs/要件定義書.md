## 3. 機能ごとの要件

### 3-1. カード作成（最優先）

**解決したい困りごと：** 職人は「自分の技術をどう説明するか」自体が困りごとの一つ。
空欄を渡して書かせても、良い文章は出てこない。

**やり方：**

```
1. 職人が質問に答える（短くてよい。単語でもよい）
2. AI が答えを組み立てて、日本語3文＋英訳を作る
3. 職人が直せる。直したものが保存される
```

**AIの置き場所：** 文章の「作成の補助」であって「校閲」ではない。
答えが短いときは AI が掘り下げる質問を返す。

**要件：**

- 職人の負担は**初回15分以内**（8/19 の方針）
- 質問の数は未決 → **5問で仮置きする**（設計書で確定）
- AI が落ちても**カードは作れること**（入力をそのまま保存する経路を必ず持つ）
- **APIキーはサーバー側のみ。**ブラウザに渡さない

### 3-2. カード表示

フロントエンドの画面優先順（8/28 に確定）に合わせる。

```
ホーム画面 → カード閲覧 → 職人プロフィール → 検索結果
→ ログイン → サインアップ → いいね閲覧 → カード登録
```

**カードの単位は「品」**（職人の作品1つ＝1枚）とする。

**これは仕様書と一致している。**仕様書にこうある。

> 同じ伝統名（name）の記事は複数の職人から投稿されうる。
> ユーザー側のマッチングはname単位でグルーピングして扱う。

つまり**データは品単位、マッチング画面だけが伝統名でグループ化して表示**する設計。
「種類か品か」の対立は、データの持ち方ではなく**表示の話**だった。

本書では**グループ化をやめて品をそのまま出す**。理由は2つ。

- 伝統名でまとめると、国指定の工芸品が約200件しかないため**すぐ在庫が尽きる**
- フロントエンドが「ホームでジャンル選択 → マッチング」にするため、
  ジャンルで絞ったうえにグループ化すると候補が数件しか残らない

グループ化に戻すのは表示側の1箇所を変えるだけで済む。**後戻りできる。**

### 3-3. いいね

ログインしたユーザーが、カードにいいねを付けられる。一覧で見返せる。

### 3-4. ユーザー登録・ログイン

**捨てない**（フロントエンドが18枚の画面設計に組み込み済みのため）。

ただし**最小限にする。** メール＋パスワード。職人か利用者かの区別だけ持つ。
国籍・年齢・言語能力などの項目は、**登録時には聞かない**（後から足せる）。

### 3-5. 検索（完了済み）

段1 キーワード → 段2 シノニム → 段3 ベクトル。地域・タグのフィルタ。
**AIは登録時に1回だけ。検索のたびには呼ばない。**この方針は変更しない。

### 3-6. 英語対応

カード作成時に日本語と英語を同時に生成して両方保存する。
検索時に翻訳は**しない**（コストが検索回数に比例するため）。

## 4. 使う技術

```
実行環境   Cloudflare Workers
FW         Hono
DB         Cloudflare D1（SQLite）
埋め込み   Workers AI（検索の段3。既に稼働）
文章生成   Gemini 2.5 Flash（無料枠 10 RPM / 500 RPD）
言語       JavaScript（ES Modules）
```

**文章生成に Workers AI を使わない理由：** 日本語の生成品質が弱く、
ここは品質がそのまま製品価値になるため。埋め込みは日本語の巧拙が関係ないので Workers AI のまま。
