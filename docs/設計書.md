## 3. カード作成（本体）

### 3-1. 何が問題か

職人の困りごとの一つが「自分の技術をどう説明するか」そのもの。
**空欄を渡して書かせても、良い文章は出てこない。**
仕様書の方式（職人が説明文を書く → AIが3文に整える）は、
**元の文の水準が低いと、整った平凡な文章になるだけ**で終わる。

### 3-2. 解決の形

**AI の仕事は「文章の作成の補助」であって「校閲」ではない。**

```
1. 職人が5つの質問に答える（単語でもよい）
2. 答えが短い項目だけ、AIが1つ掘り下げる質問を返す
3. 集まった答えから、AIが日本語3文＋英訳を作る
4. 職人が直せる。直したものが保存される
```

### 3-3. 質問（5問）

**工芸品にも無形文化財にも使える形にする。**
「作る」「演じる」の両方に答えられる言い方を選ぶ。

| # | 質問 | 何を引き出すか |
|---|---|---|
| 1 | 何を作って（演じて）いますか。ひとことで。 | 主題 |
| 2 | その中で、いちばん手間がかかるのはどこですか。 | 具体的な工程 |
| 3 | そこは、ひとりでできるまでどれくらいかかりましたか。 | **年数。事実なので答えやすい** |
| 4 | よそと違うと思うのは、どんなところですか。 | 差 |
| 5 | はじめて見る人に、どこを見てほしいですか。 | 見どころ |

**3が肝。**職人は自慢が苦手だが、**年数は事実なので抵抗なく答えられる。**
そして「この工程だけで10年」は、それ自体が最も人を動かす情報になる。

伝統名・職人名・場所・タグは**フォームで既に取れている**ので質問しない。
入力の負担を15分以内に収めるため。

**この5問は仮ではなく、本書での決定とする。**変えるときは本書を先に直す。

### 3-4. AI の呼び方

```
文章生成   Gemini（下記）      日本語3文 + 英訳 を1回の呼び出しで
埋め込み   Workers AI bge-m3   検索の段3。既存のまま変更しない
ふりがな   Gemini（同上）      仕様書は gpt-oss-20b だが、モデルを増やしたくない
```

#### モデル名はエイリアスを使う

**`gemini-2.5-flash` はバージョン固定で指定すると 404 になる。**（2026-09-03 実測）

```
models/gemini-2.5-flash is no longer available to new users
```

ListModels には残っているが `generateContent` では拒否される。
**バージョンを固定すると、提供終了のたびに黙って止まる。**

そこで `-latest` エイリアスを使う。

```
gemini-flash-lite-latest   ← 採用
gemini-flash-latest        ← 使えなかった（下記）
```

**`gemini-flash-latest` は 503（高負荷）で使えない。**（2026-09-03 実測）
間隔を空けて6回試して6回とも失敗。`lite-latest` は安定して成功する。

**エイリアスは中身が勝手に変わるという欠点がある。**それでも固定より安全と判断した
（固定は今回 404 で止まった）。**発表の直前に1回、実際に叩いて確認すること。**

#### 【重要】503 は現実に起きる

`latest` が6回連続で 503 を返した。**`lite-latest` にも同じことが起きうる。**

そのため、フォールバックは「キーが無いとき」だけでなく
**「API が 5xx / タイムアウト / 不正な JSON を返したとき」にも必ず効くこと。**

```
どの失敗でも → ai:false でカードは作れる
              エラーを client に返して登録を止めない
```

**発表中に 503 が返ってカードが作れないのが、最悪の負け方。**
キー無しの経路だけ確認して安心しないこと。

（2026-09-03 決定。当初は「Gemini 2.5 Flash」と書いていたが、404 のため変更した）

**API の形**

```
POST /api/introduce/artisan/compose

リクエスト
{
  "name": "輪島塗",
  "answers": ["椀と箸", "下地を塗って研ぐ", "10年", "下地を20回重ねる", "縁の薄さ"],
  "followups": []                       // 省略可。既定は []
}

レスポンス（掘り下げが要るとき）
{ "ja": null, "en": null, "ai": true,
  "followup": { "index": 1, "question": "その工程で、いちばん失敗しやすいのはどこですか" } }

レスポンス（完成）
{ "ja": ["文1","文2","文3"], "en": ["s1","s2","s3"], "ai": true, "followup": null }
```

掘り下げが返ったら、フロントはその答えを `followups` に足して**もう一度同じAPIを呼ぶ。**

```json
"followups": [
  { "index": 1, "question": "その工程で…", "answer": "湿度が高い日は乾かない" }
]
```

**掘り下げは1周だけ。**`followups` が空でないリクエストには、
**必ず3文を返す**（`followup` を返さない）。

**なぜ1周に限るか：**無限に往復すると職人が離脱し、トークンも燃える。
要件は「初回15分以内」なので、往復は最小にする。

**サーバーは状態を持たない。**毎回 `answers` と `followups` を全部受け取って組み立てる。
セッションに途中経過を貯めない（実装が増え、消し忘れが出るため）。

**入出力の内訳**

```
入力  5問の質問と答え + 掘り下げの往復 + 伝統名 + 職人名 + 場所
出力  上記の JSON
```

**掘り下げの判定は2段に分ける。**（2026-09-02 決定）

| 何を | 誰が | なぜ |
|---|---|---|
| 空欄かどうか | **コード** | キーが無くても動作確認できる。元の質問をそのまま出し直すだけ |
| 薄いかどうか＋質問の文言 | **Gemini** | 具体的に聞けないと意味がない |

**空欄に「もう少し詳しく」と返すのは掘り下げではなく必須項目チェック。**
元の質問を出し直せば足りる。

**効くのは、答えはあるが薄いとき。**「いろいろ」と書かれたときに
「いろいろ、とは。漆を塗る回数ですか、乾かす時間ですか」と具体的に聞けると
良い材料が出る。これはコードでは書けない。

**文字数のしきい値は置かない。**「この答えでは3文が書けない」かどうかをモデルに判断させる。

**往復は増やさない。**同じ呼び出しの中で、3文を返すか `followup` を返すかを分岐させる。

#### 分野の観点をプロンプトに与える

伝統工芸・伝統芸能の説明文で説得力を生むのは何か、を Gemini に渡す。

```
工程の具体名        下地、研ぎ、燻し、地無し
回数・時間・年数    20回重ねる、10年かかる
材料の産地や状態
失敗しやすい条件    湿度が高い日は乾かない
```

これがあると「もう少し詳しく」ではなく「その下地は何回重ねますか」と聞ける。

#### 3文の書き方（プロンプトで指示する）

**事実だけ並べても平凡になる。**並べ方まで指示する。

| 守ること | なぜ |
|---|---|
| **1文目に、いちばん強い事実を置く**（年数・回数・具体的な数字） | 「10年」「20回以上」がその職人の凄み。埋もれさせない |
| **報告調にしない**（「〜である」「〜している」を避ける） | 第三者の解説文になり、作り手の顔が消える |
| **答えに無い形容詞を足さない**（丁寧な、美しい、伝統的な…） | 事実ではないうえ、どの工房にも書ける文になる |
| **質問と文を1対1で対応させない** | 穴埋めに見える。5問の答えを組み替えて3文にする |
| **短く言い切る** | 修飾を重ねるほど平凡になる |

悪い例（実際に出力されたもの）

```
椀と箸を手がける輪島塗の職人は、下地の漆を塗って研ぐ工程に最も手間をかけている。
その下地をひとりでできるようになるまでには10年かかり、20回以上も重ねるのが特徴である。
```

**何も嘘は書いていないが、一番強い「10年」「20回」が2文目に埋もれている。**
1文目は誰にでも書ける。「丁寧な手仕事」は答えに無い形容。

狙う形

```
下地の漆を、20回以上重ねる。
ひとりでできるようになるまでに10年かかった。
```

**この節は「答えに無いことを書かない」より優先度が低い。**
言い回しを整えるために事実を足すのは禁止。**足りないなら短い3文でよい。**

（2026-09-03 追加。実際の出力が平凡だったため）

#### 【最重要】分野の知識は質問にだけ使う

> **分野の知識は、質問を作るために使う。本文に事実を足すためには使わない。**
> **答えに書かれていないことは書かない。**足りないなら質問として返す。

ここを曖昧にすると、AI が「輪島塗は百以上の工程で分業され」といった**一般論を
勝手に本文へ書き込む。**それは職人の言葉ではないので、**この製品の価値そのものが消える。**
プロンプトに明示的に禁止として書くこと。

- **答えが空の項目があるときは、`followup` に元の質問をそのまま入れて返す（コード側）**
- **答えはあるが3文を書くには足りないときは、`followup` に具体的な質問を入れて返す（Gemini側）**
- 3文ちょうどにする。4文以上になったら**コード側で先頭3文を切り出す**（仕様書と同じ扱い）
- **答えに書かれていないことを足さない**ようプロンプトで明示する

**キーの扱い**

```
GEMINI_API_KEY   Workers の Secret。 npx wrangler secret put GEMINI_API_KEY
                 ブラウザには絶対に渡さない。フロントから直接叩かせない
```

**落ちたときの逃げ道（必須）**

Gemini が落ちても**カードは作れること。**
失敗したら、5問の答えをそのまま連結して `description` に入れて保存する。
レスポンスに `ai: false` を入れてフロントに伝える。
**発表中にAIが落ちてもデモが止まらないようにするため。**

## 4. 認証

### 4-1. パスワード

WebCrypto の PBKDF2-SHA256。ソルトは16バイト乱数。
**外部ライブラリを入れない**（Workers で動く保証を確かめる時間がない）。

**反復回数は 10,000。**`features/auth/crypto.js` の名前付き定数1箇所に置く。

```js
// 【重要】Workers 無料プランは CPU 10ms/リクエスト。
// 大きくすると本番の signup / login だけが落ちる。
// ローカルの wrangler dev では CPU 制限が効かないので再現しない。
const PBKDF2_ITERATIONS = 10000;
```

**これはデモ用の妥協であり、実運用の水準ではない。**

| | |
|---|---|
| OWASP の推奨 | PBKDF2-HMAC-SHA256 で **600,000回** |
| 本書の値 | **10,000回**（推奨の約60分の1） |
| なぜ下げたか | Cloudflare Workers 無料プランの CPU 上限が 1リクエスト 10ms。
10万回でも超える。**本番の signup / login だけが落ちる** |
| なぜローカルで気づけないか | `wrangler dev` は CPU 制限を強制しない。**デプロイして初めて落ちる** |
| 実運用でどうすべきか | Workers 有料プラン（CPU 30秒）に上げて反復回数を戻す。
またはハッシュ処理を別サービスへ逃がす |

**このアプリのアカウントはデモ用**で、実在の個人情報も決済情報も入れない。
発表中にログインできないほうが致命的、という判断で下げている。

**実データを入れる段階になったら、必ず見直すこと。**

（2026-09-02 決定。当初は10万回と書いていたが、CPU上限の調査により変更した）

### 4-1-b. パスワードの条件

**NIST SP 800-63B の現行版に合わせる。**

```
最小        12文字
最大        制限しない。切り詰めない
文字種の強制 しない（大文字・数字・記号を必須にしない）
使える文字   印字可能な文字すべて。スペースも Unicode も可
前後の空白   削らない（パスワードの一部として扱う）
拒否するもの よくあるパスワード上位100件 / メールアドレスと同一の文字列
```

**大文字・記号を必須にしない理由：**必須にすると人は `Password1!` を作る。
規則は満たすが辞書攻撃に弱い。しかも規則を満たすために短くなる。
NIST は現行版で **composition rules を明示的に廃止**している。効くのは長さ。

**なぜ NIST の下限8ではなく12にしたか：**
このプロジェクトは PBKDF2 が1万回（推奨の60分の1）と弱い。
ハッシュが弱いぶん、流出時の総当たりが安くなるので、長さで補う。

**なぜ NIST 推奨の15にしなかったか：**
発表で壇上から打つとミスするため。**デモ用アカウントは事前に作っておくこと。**

**流出パスワードの照合（Have I Been Pwned API）は入れない。**
signup ごとに外部通信が増え、落ちたときの分岐も増える。
埋め込みの上位100件で、デモで踏む範囲は防げる。

（2026-09-02 決定）

### 4-2. セッション

乱数32バイトの hex を `sessions` に保存し、Cookie で返す。

```
Set-Cookie: sid=<token>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=604800
```

**JWT を使わない理由：**失効させられない。デモ中に消したくなったときに困る。
DBに置けば `delete from sessions` で全部切れる。

**`HttpOnly` にする理由：**JS から読めなくする。XSS でトークンを盗まれないため。

**`SameSite=Lax` でよい理由：**フロントエンドを**この Worker と同じところに載せる**ため
（2026-09-02 確認済み）。同一オリジンなので Cookie は問題なく送られる。

**別オリジンにするなら `SameSite=None; Secure` が要る。**そのときは常時HTTPSが前提になり、
ローカル確認の手順も変わる。**構成を変えるなら、実装より先にここを直すこと。**

### 4-3. ミドルウェア

（2026-09-02 修正。当初は `/api/introduce/user/*` 全体に掛けると書いていた）

## 6. 画像

**Cloudflare Workers KV に、生のバイト列のまま保存する。**
R2 は課金設定が要るため不採用。Supabase Storage は筋がいいが、
2日で2つ目のデータストアを足す余裕がないため見送る。

**base64 にしない。**（仕様書は base64 だが、こちらは変える）

```
5MB の画像 → base64 で約6.7MB
取り出すたびにデコードが必要 → Workers 無料プランは CPU 10ms/リクエスト
```

**PBKDF2 と同じ「ローカルでは通って本番だけ落ちる」型になる。**
KV は `ArrayBuffer` をそのまま `put` できるので、base64 にする必要がない。
デコードが消えて CPU を食わず、容量も33%減る。

取り出しは `get(key, "stream")` して、そのままレスポンスに流す。

```js
await c.env.teame_images.put(key, arrayBuffer, {
  metadata: { content_type: file.type },   // 何の画像かを覚えておく
});

const { value, metadata } = await c.env.teame_images.getWithMetadata(key, "stream");
return new Response(value, { headers: { "content-type": metadata.content_type } });
```

**`metadata` に `content_type` を必ず入れること。**
入れないと、取り出したときに何の画像か分からず返せない。

（2026-09-02 決定。当初は仕様書に合わせて base64 と書いていたが、CPU上限のため変更した）

```
バインディング   teame_images   KV Namespace
キー             card-image:{uuid}
上限             1枚5MB / 1カード3枚まで（サーバー側でも強制する）
許可             image/* のみ
```

```
POST /api/introduce/artisan/upload-image   1枚ずつ。 → { key }
GET  /api/introduce/image/:key             KVから取り出してデコードして返す
```

登録時に `image_keys` の配列を送り、`card_images` に `sort_order` 付きで保存する。

**`GET /image/:key` は認証を掛けない**（カード閲覧で誰でも見るため）。
ただし**キーは uuid なので推測できない。**

## 7. 住所と地図

**Google Maps を使わない**（チーム方針）。すべて OpenStreetMap 系で揃える。

| 用途 | 使うもの | キー |
|---|---|---|
| 郵便番号 → 住所 | zipcloud API | 不要 |
| 屋号・住所 → 候補＋緯度経度 | Nominatim（OSM） | 不要 |
| 緯度経度 → 住所（地図クリック） | Nominatim 逆引き | 不要 |
| 地図表示 | Leaflet + OSM タイル | 不要 |

```
GET /api/introduce/artisan/postal?code=9280001     zipcloud を中継
GET /api/introduce/artisan/geocode?q=輪島塗会館     Nominatim を中継（上位3件）
GET /api/introduce/artisan/reverse?lat=&lng=       Nominatim 逆引き
```

**サーバー側で中継する理由：**ブラウザから直接叩くと CORS と
Nominatim の利用規約（User-Agent 必須）を守れないため。

**Nominatim の制約：** 1秒1リクエストまで。`User-Agent` を必ず付ける。
個人の小さな工房はヒットしないことが多い（仕様書も指摘済み）。
**そのときは「郵便番号で大まかに → 地図をクリックして正確な位置」**の経路を使う。

緯度経度は `card_geo` に保存する。無い場合は検索機能と同じく
都道府県の代表座標（`features/search/regions.js` の `coordsOf`）で代替する。

地図表示は `features/search/ui.js` の実装を持ってくる。
**CDN が落ちる場合に備えて try/catch で包む**（AGENTS.md の落とし穴）。

## 8. 検索機能との接続（忘れやすい）

**カードを作っただけでは、段3（あいまい検索）に出てこない。**
`card_embedding` に埋め込みが無いため。

```
POST /api/introduce/artisan   → カード保存後、そのカードの埋め込みを1件だけ生成する
```

全件 reindex を呼ばない。**1件だけ**生成する。
失敗しても**カードの保存は成功させる**（段1・段2では検索できるため）。

**`card_embedding` に直接 INSERT を書かないこと。**
このテーブルは検索機能の所有物で、`features/search/db.js` に
「検索側が書き込む唯一の場所」と明記してある。
紹介機能から生SQLを書くと、所有権の原則（AGENTS.md 絶対に守ること1）が形骸化する。

**検索機能が公開している関数を import して呼ぶ。**

```js
import { embed, cardToText, EMBED_MODEL } from "../search/embed.js";
import { saveEmbedding } from "../search/db.js";

// カード保存後
try {
  const [vec] = await embed(c.env.AI, [cardToText(card)]);
  await saveEmbedding(db(c), card.id, vec, EMBED_MODEL);
} catch (e) {
  console.error("[introduce] 埋め込み生成に失敗", e);  // 保存は成功させる
}
```

**これは所有権の違反ではない。**テーブルを直接触るのが違反であって、
所有者が公開している関数を呼ぶのは正しい使い方。

## 8-2. 英語クエリと段3（要検証）

段3の埋め込みは `cards` の日本語列（`cardToText`）から作っている。
`card_i18n` の英語は埋め込みの対象外。

英語のクエリが日本語の説明文に当たる可能性は十分ある。
